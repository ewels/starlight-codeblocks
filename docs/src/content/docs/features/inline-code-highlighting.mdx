Starlight shows inline code in the prose in one colour, with no syntax highlighting. A short expression such as a function call is then harder to read than the same code in a block. A `{:lang}` suffix at the end of the inline code gives it the syntax colours of that language.

export const basic = `
Call \`await fetch(url){:js}\` and check \`res.ok{:js}\` before you read the body.
`;

<Example code={basic}>

Call `await fetch(url){:js}` and check `res.ok{:js}` before you read the body.

</Example>

The two pieces of inline code get the colours and the background of the site's code blocks. The plugin removes the suffix, so readers see only the code.

## Syntax

| Syntax | Where | Example |
|---|---|---|
| `` `<code>{:<lang>}` `` | Inside the backticks, at the end of the code | `` `res.ok{:js}` `` |
| `` `<code>`{:<lang>} `` | Directly after the closing backtick | `` `res.ok`{:js} `` |

`<lang>` is a language name or alias that Expressive Code knows, the same as on a fence line: `js`, `py`, `sh`, `css` and others. Languages that the site adds in the `shiki.langs` option of Expressive Code work too. The suffix must follow the code or the backtick with no space between them.

Use the suffix inside the backticks. It is the syntax of rehype-pretty-code, and it is valid in `.md` and `.mdx` files with no change. Inline code that contains a backtick keeps its suffix as text, so that a page can show the syntax, as this one does.

<Aside type="caution">
MDX reads a `{:js}` after the closing backtick as a JavaScript expression, and the build fails. Write a backslash before it: `` `res.ok`\{:js} ``. Some plugins read `.md` files as MDX too, such as starlight-versions and starlight-md-txt, so the backslash is needed in `.md` files on those sites. The backslash works in `.md` files on every site.
</Aside>

## Behaviour

- The inline code uses the site's Expressive Code themes: the background and the token colours of the dark theme and the light theme.
- The colours change with Starlight's theme menu, the same as the code blocks.
- The colours have the same contrast correction as the code blocks.
- The plugin removes the suffix from the page, in both forms.
- Inline code without a suffix does not change.
- If Expressive Code does not know the language, the code shows as normal inline code and the build logs a warning with the file name. The plugin removes the suffix.
- The highlighting happens at build time, so it works without JavaScript. Pages with no code blocks get the colours too.
- The highlighted code is a normal `code` element. Screen readers and the copied text get the same characters as before.

## Options

Inline code highlighting has no options. Turn the feature off for the whole site with `inlineHighlighting: false`:

```js title="astro.config.mjs"
codeblocks({
  inlineHighlighting: false,
});
```

With `inlineHighlighting: false`, the suffix stays in the prose as text.

## Examples

A shell command in a sentence:

export const shell = `
Install the package with \`pnpm add starlight-codeblocks{:sh}\`, then restart the dev server.
`;

<Example code={shell}>

Install the package with `pnpm add starlight-codeblocks{:sh}`, then restart the dev server.

</Example>

A CSS declaration and a Python expression in a list, with the suffix after the backtick:

export const list = `
- Hide the element with \`display: none\`{:css}.
- Round the value with \`round(total / count, 2)\`{:py}.
`;

<Example code={list}>

- Hide the element with `display: none`\{:css}.
- Round the value with `round(total / count, 2)`\{:py}.

</Example>

## Limitations

- Inline code cannot use the attributes or directives of code blocks, such as focus or line states.
- The plugin does not support the token form of rehype-pretty-code, such as `{:.entity.name.function}`.
- The code must be on one line. Expressive Code highlights it as a code block of one line. An unclosed string colours the rest of the code as a string.

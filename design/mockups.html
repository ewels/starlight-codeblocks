Code block features for Starlight

The agreed design for starlight-codeblocks (working name): 24 features for the first release. Each section shows what an author writes, what a reader sees and where the feature lives. The mockups are the visual and behavioural target for the build. Where this page and SPEC.md disagree, SPEC.md wins.

This block is a working mockup. Hover or tab into it to bring the blurred lines back, and select the numbered marker to read its annotation.

Assumptions

Astro 7 and Starlight 0.42 on the Sätteri Markdown pipeline, with Expressive Code 0.44 rendering code blocks. There are no remark or rehype plugins, and nothing relies on Shiki’s JavaScript transformers. Everything ships as one Starlight plugin that registers Expressive Code plugins, client scripts and components as needed. The package would also export the Expressive Code plugins on their own for sites that don’t use Starlight.

The mockups approximate Starlight’s default dark code style. Their syntax colours come from a small hand-written tokeniser, not the real highlighter, so treat colours as indicative.

Expressive Code plugin
Runs at build time on each code block. Output is static HTML and CSS, so it costs readers nothing and works without JavaScript.
Client script
A small script the Starlight plugin adds to pages, for behaviour static HTML can’t manage: syncing values, reacting to prose, remembering choices.
Sätteri plugin
An mdast or hast plugin on Astro’s Rust Markdown pipeline, for syntax outside code blocks such as directives and inline code. Whether a Starlight plugin can register one still needs checking.
Component
An Astro component used from MDX, for layouts that span several blocks or the page.
Effort
Small is one plugin hook and some CSS. Medium adds several hooks, a client script or tricky layout. Large means a new component, an external dependency or an open design question.

Inside the code block

Build-time features that change how a single block renders.

Focus

Blur the lines that don’t matter so readers look at the ones that do. Hovering or tabbing into the block brings everything back.

Authors pick lines with focus={…} in the fence or [!code focus] in a comment. Readers see the focused lines sharp and the rest blurred and faded. The copy button still copies the whole block.

Lives in
Expressive Code plugin.
Effort
Small. The prototype from earlier in this chat already works.
Seen in
VitePress, Mintlify, Code Hike.
Watch out for
Blur makes the other lines unreadable for some readers, so offer a dim-only style setting, and drop the transition under reduced motion.

Line states

Tint lines as errors, warnings or notes, with an optional message at the end of the line, like an editor’s diagnostics.

The built-in states are error, warning and info, set by line number in the fence or by comment. Text after the comment marker becomes the message. Sites can define their own names and colours in config, such as todo or deprecated. Messages are left out of the copied text.

Lives in
Expressive Code plugin.
Effort
Small.
Seen in
VitePress (error and warning), Docusaurus magic comments (custom names).
Watch out for
Colour alone can’t carry the meaning. Each state needs an icon or text label for colour-blind readers and screen readers, not just the tint.

Comment notation

Put markers in the code instead of line numbers in the fence, so they move with the code when you edit it.

The plugin looks for [!code …] in the block’s own comment syntax (//, #, --, <!-- -->). It removes the comment from the rendered code and the copied text, then hands the line to the matching feature: highlight, ++, --, focus, error, warning and so on. The syntax matches VitePress, so migrated pages work unchanged.

Lives in
Expressive Code plugin, as a preprocessing step that feeds the other plugins.
Effort
Small to medium.
Seen in
VitePress, Shiki’s notation transformers, Code Hike.
Watch out for
Languages without comments, such as JSON; use jsonc or the fence meta there. It also needs an escape so docs can show the marker literally.

Inline callouts

A short note in a bubble directly above a line, pointing down at the token it explains.

A comment line names the token and gives the text. The callout applies only to the line directly below the comment. The comment disappears and the bubble takes its place, pointing down at the token’s column. The bubble is plain HTML and CSS, supports inline code and links, and stays out of the copied text.

Lives in
Expressive Code plugin.
Effort
Medium. Column alignment has to cope with tabs, line numbers and word wrap.
Seen in
Code Hike.
Watch out for
Long bubbles on narrow screens. They should wrap within the block rather than widen it.

Annotations

Numbered markers at the end of lines that open an explanation, keeping the code itself uncluttered.

Text after [!annotate] becomes a marker button. Selecting it opens a popover, and Escape or a click elsewhere closes it. Markers number themselves in order and are skipped by the copy button. The native popover attribute handles opening and closing, so the only script is a positioning fallback for browsers without CSS anchor positioning.

Lives in
Expressive Code plugin, plus a tiny client script.
Effort
Medium.
Seen in
Material for MkDocs, where it is one of the flagship features.
Watch out for
The explanation lives in the comment, so long notes make long source lines. Material’s style, with the notes in a list after the block, would need a Sätteri plugin.

Footnotes

Numbered badges on lines, with the explanations listed under the block where readers see them without clicking.

A comment line with [!ref] attaches its text to the line below. Selecting a badge highlights its whole line and its note, and scrolls the note into view if needed. Selecting a note does the same the other way round, scrolling to the line. Selecting anywhere else clears the highlight.

With footnotes="sticky", the list stays pinned to the bottom of the viewport while the block is on screen. The default is not sticky. Scroll through the second block to see it.

Lives in
Expressive Code plugin, plus a small client script for the highlight.
Effort
Small.
Seen in
Code Hike.
Watch out for
Overlap with annotations. One syntax with a display setting (popover, footnotes or side by side) may be better than three separate features.

Hidden lines

Hide the imports and set-up that readers need to run an example but not to understand it.

Lines listed in hidden={…}, or marked with [!code hide], are left out of the rendered block. A dashed marker shows where each run of hidden lines sits. Selecting a marker shows or hides that run only. The header button shows every run, or hides them all if they are all showing. The copy button always includes hidden lines, so pasted code still runs. Unlike Expressive Code’s collapsible sections, hidden lines take up no space until the reader asks for them.

Lives in
Expressive Code plugin, with a few lines of script for the toggle.
Effort
Small.
Seen in
mdBook and rustdoc, which hide lines that start with # .
Watch out for
Readers pasting code they haven’t seen. The markers and the header button make it clear that lines are hidden.

Smart shell copy

Terminal blocks can show prompts and output, but copying gives only the commands.

Lines that start with a prompt such as $ are commands. Everything else is output and is dimmed. The copy button says Copy commands, strips the prompts and drops the output. Commands continued with a trailing backslash stay together. Try the button: the copied text appears underneath.

Lives in
Expressive Code plugin, if a plugin can change the copy button’s payload. That needs checking; otherwise it takes a small script.
Effort
Small.
Seen in
A proposed mdBook change. Expressive Code’s terminal frames only drop comment lines when copying.
Watch out for
# is both a root prompt and a comment, so prompts should be configurable per site.

Word-level diff

In a diff, highlight only the words that changed, not whole lines.

Removed and added lines next to each other are paired and compared token by token, and the changed tokens get a stronger tint. It applies automatically to diff blocks, and the underlying language is still highlighted.

Lives in
Expressive Code plugin, building on its inline text markers.
Effort
Medium.
Seen in
GitHub and GitLab diffs.
Watch out for
Pairing gets unreliable when a change adds or removes several lines at once. Fall back to whole-line tints when paired lines differ too much.

Visible whitespace

Show spaces and tabs as faint glyphs where indentation changes the meaning.

With the whitespace flag, spaces render as dots and tabs as arrows. Leading whitespace is shown by default, or all of it with whitespace="all". The example shows why it matters: the second recipe is indented with spaces, which Make rejects. Copying gives the real characters.

Lives in
Expressive Code plugin.
Effort
Small.
Seen in
VS Code, and Shiki’s render-whitespace transformer.
Watch out for
Visual noise. Keep it opt-in per block.

Colourised brackets

Colour matching brackets by nesting depth, as VS Code does, so dense one-liners are easier to read.

The brackets flag cycles three colours by depth and ignores brackets inside strings and comments. Hovering a bracket outlines its partner. The colours would be tuned per theme.

Lives in
Expressive Code plugin, reading the highlighted tokens.
Effort
Small to medium.
Seen in
VS Code, and Shiki’s colourised-brackets transformer, which can’t be used directly on this stack.
Watch out for
Noise in short snippets. Best as a per-block flag or limited to certain languages.

Token links

Turn any token into a link, from a comment above the line.

[!link /token/ url] links the first match of the token on the next line. The comment disappears and the token gets a subtle underline.

Lives in
Expressive Code plugin.
Effort
Small.
Seen in
Code Hike.
Watch out for
Overlap with API auto-linking, which covers the common case with no markup. Token links are for one-offs.

API auto-linking

Names in examples link to their reference pages automatically, with a hover card showing the signature and summary.

Authors write nothing extra. Each language has an adapter that finds names in a block and resolves them against one or more indexes. Names an adapter can’t resolve stay plain text.

The Python adapter reads the imports in each block. It resolves names against the project’s own starlight-pydocs pages, and against objects.inv inventories for other libraries, the same files Sphinx’s intersphinx uses. The Nextflow adapter resolves channel factories and operators against the Nextflow docs, and processes against the pipeline’s own module reference. Sites can register more adapters in config. Hover or focus a name in either block.

Lives in
Expressive Code plugin with a language-adapter interface. The Python adapter shares an object index with starlight-pydocs.
Effort
Large. Each adapter needs a parser for its language at build time. Start with imports and attribute chains.
Seen in
sphinx-codeautolink.
Watch out for
A wrong link is worse than none, so adapters should only link names they can resolve with certainty.

Expandable blocks

Long blocks show their first few lines with a fade and a button to reveal the rest.

expandable caps the block at twelve lines, or expandable={8} at eight. The button says how many lines there are. Using hidden="until-found" where browsers support it means find-in-page still finds text in the collapsed part and expands the block.

Lives in
Expressive Code plugin, plus a few lines of script.
Effort
Small.
Seen in
Mintlify.
Watch out for
Printing, which should expand everything.

Open in playground

A button in the frame that opens the example in an online playground with the code already filled in.

playground="…" adds the button. The TypeScript and Rust playgrounds are built in. Sites register their own in config, each with a label and one of two ways to send the code: a URL builder, for playgrounds that take code in the URL, or a form post, for playgrounds such as StackBlitz that take multi-file projects. URL playgrounds need no client script.

Lives in
Expressive Code plugin, with one adapter per playground.
Effort
Small per playground.
Seen in
mdBook’s Rust examples, the TypeScript handbook.
Watch out for
Code has to be complete to run. This pairs well with hidden lines.

Across the page

Features that connect a block to the prose around it, to other blocks or to the reader’s own input.

Code mentions

Hovering a phrase in the prose highlights the lines it refers to.

Lines are tagged with [!mention name] and the prose links to #mention:name, so the page stays plain Markdown. A client script pairs each link with the tagged lines in the next block and highlights them on hover or keyboard focus. Selecting a link scrolls the block into view.

Lives in
Expressive Code plugin for the tags, plus a client script.
Effort
Medium.
Seen in
Code Hike.
Watch out for
starlight-links-validator may flag the #mention: links as broken anchors unless they are excluded.

Line permalinks

Select a line number to get a link to that line. Opening the link scrolls to the line and highlights it.

Blocks with an id get clickable line numbers, and Shift-click extends the selection to a range. On page load the script reads the address and highlights the lines. In the mockup, the address bar above the block updates instead of the real one.

Lives in
Expressive Code plugin for ids and line numbers, plus a client script.
Effort
Small to medium.
Seen in
GitHub.
Watch out for
Ids have to stay stable when blocks are added to a page, so they should come from an explicit id or the title, never the block’s position.

Fill-in placeholders

Placeholders such as YOUR_TOKEN become input fields. What the reader types fills every block on the site and the copied text.

The fence lists the literal strings to treat as fields, so nothing in the code can clash with the syntax. Each field is as wide as its text and grows as the reader types. Values stay in the reader’s browser and are never sent anywhere. Type in one block and watch the other update, then try the copy button.

Lives in
Expressive Code plugin for the fields, plus a client script.
Effort
Medium.
Seen in
API references that fill in the reader’s own keys.
Watch out for
Secrets saved in a shared browser. Offer a this-tab-only setting and a clear button.

Code switcher

One block holds several variants, switched from a menu in the title bar. The choice sticks across the site.

Consecutive fences inside a :::code-switcher directive become one block. Each fence can set label="…" for its menu entry; without a label, the menu shows the language name. Blocks with the same sync key switch together and remember the choice, so a reader who picks pnpm once sees pnpm everywhere. It works like Starlight’s Tabs with syncKey, but takes one menu instead of a row of tabs. Try the menus below: the second and third blocks share a key.

Lives in
A Sätteri plugin for the directive, or an MDX component if that isn’t possible, plus a client script.
Effort
Medium.
Seen in
Code Hike, Mintlify.
Watch out for
Overlap with Tabs. The docs should say when to use which.

Token transitions

Step through versions of a block and watch the code move between them, so readers see what changed.

Successive fences inside a component become steps, each with an optional step="…" label. The numbered steps sit at the left of the title bar, joined by a line that fills in as the reader moves forward, with the current label beside them. Previous and Next buttons sit at the right. The arrow keys also move between steps when a step has focus. Unchanged lines slide to their new place and new lines fade in. The mockup animates whole lines; the real version animates tokens, using the precompiled mode of @shikijs/magic-move fed with Expressive Code’s tokens.

Lives in
Component, plus a client script.
Effort
Large.
Seen in
Slidev, Code Hike.
Watch out for
Bundle size, and reduced motion, where steps should switch instantly.

Scrollycoding

Prose steps scroll past a sticky code block, and each step changes which lines are in focus.

A component holds one block and a list of steps, each naming the lines to focus. Scroll inside the frame to try it. On narrow screens the real version would fall back to a focused copy of the block under each step.

Lives in
Component, plus a client script. It reuses Focus.
Effort
Large.
Seen in
Code Hike.
Watch out for
Starlight’s content column is narrow for two columns, so this may need the splash template or a wider layout.

Side-by-side annotations

Explanations sit in a column beside the code. Hovering a note highlights its line, and hovering a line highlights its note.

It uses the same [!annotate] syntax, with annotations="side" on the fence. The notes form a numbered column aligned to the top of the block, and the column sticks to the top of the viewport while the block scrolls past. Numbers on the lines match the numbers in the column. On narrow screens the notes drop below the block as a numbered list.

Lives in
Expressive Code plugin and CSS, with a little script for the hover link.
Effort
Medium.
Seen in
GitHub Docs.
Watch out for
A column taller than the viewport can’t stick usefully. In that case it should scroll with the page.

Build last

In the first release, but built after everything else. Inline highlighting has an open question, and running code needs the most new machinery.

Inline code highlighting

Syntax colours for inline code within a sentence.

A suffix marks the language, following rehype-pretty-code’s convention. Expressive Code only handles blocks, so this needs a Sätteri hast plugin with access to a highlighter. Sätteri runs its highlighter before hast plugins, so it isn’t yet clear where that plugin would get one.

Lives in
Sätteri plugin.
Effort
Medium to large, and uncertain.
Seen in
rehype-pretty-code. There is also an open Expressive Code feature request for it.
Watch out for
Without a clean hook this could turn into maintaining a fork.

Run in the browser

A Run button executes the example in the browser and shows the output below it.

The runnable flag adds the button. Each language has a runtime adapter with two jobs: load the runtime, and run code and return its output. The plugin ships a Pyodide adapter for Python. Sites register other runtimes in config, such as a sandboxed iframe for JavaScript or a remote execution service. The runtime loads on the first click, never with the page. The mockup fakes the output.

Lives in
Expressive Code plugin for the button, plus a client script with the runtime interface. The script loads only on pages with runnable blocks.
Effort
Large. Keep the adapter interface to those two functions.
Seen in
mdBook, JupyterLite.
Watch out for
Pyodide is a download of several megabytes, so it must never load before the reader asks.

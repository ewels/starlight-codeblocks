# Page structure and conventions

## File type

| Type | Use when |
| --- | --- |
| `.md` | Prose and code blocks only. Aside directives work; no components. Default choice — keeps pages portable. |
| `.mdx` | The page needs components or JSX expressions. Requires imports at the top. |
| `.mdoc` | Markdoc preset is set up and content authors want a syntax with no imports and no JS. |

Start pages as `.md` and promote to `.mdx` when a component is genuinely needed. Every `.mdx` page carries an import block that has to be maintained.

## Frontmatter

Commonly used fields:

```yaml
---
title: Page title
description: One sentence, used for meta description and search results.
sidebar:
  label: Shorter label
  order: 2
  badge:
    text: New
    variant: tip
tableOfContents:
  minHeadingLevel: 2
  maxHeadingLevel: 3
---
```

- `title` is required and renders as the `<h1>`. **Don't add an `# H1` in the body** — that produces two.
- `description` is worth writing for every page; it feeds meta tags and Pagefind results.
- `sidebar.label` when the title is too long for the nav.
- `sidebar.order` only affects autogenerated sidebar groups.
- Other fields exist (`template: splash`, `hero`, `banner`, `draft`, `prev`/`next`, `head`, `editUrl`, `slug`, `lastUpdated`). Check `https://starlight.astro.build/reference/frontmatter/` before using one from memory — this list changes.

## Headings

- Body headings start at `##`, since `title` occupies `<h1>`.
- Don't skip levels.
- Sentence case, matching Starlight's own docs.
- Every heading gets an anchor link automatically; write them so they're stable, since they end up in external links.

## Sidebar

Two approaches in `astro.config.mjs`: explicit `items` arrays, or `autogenerate: { directory: 'guides' }`. Autogeneration keys off directory structure and `sidebar.order`, and is much less work at scale — but ordering becomes implicit, so use explicit `order` values in frontmatter rather than relying on filenames.

Sidebar labels should be shorter than page titles. A nav column of wrapped three-line labels is unusable.

## Prose

- Second person, present tense, active voice. "Add the plugin to your config", not "the plugin should be added".
- Say what something does before saying how to configure it.
- Prefer a working example over a description of the syntax. Expressive Code's whole point is that examples can carry annotation, so lean on markers and labels instead of "note that on line four...".
- Link the first mention of a concept to its own page; don't re-link every occurrence.
- Code identifiers in backticks, file paths in backticks, UI labels in bold.

## Linking

Internal links use root-relative paths with trailing slashes (`/guides/getting-started/`) to match Starlight's default trailing-slash behaviour. Astro's dev server catches broken internal links only when they 404 during a crawl, so `astro build` plus `starlight-links-validator` is worth wiring into CI for a docs site of any size.

## Things worth installing

- `@expressive-code/plugin-collapsible-sections` and `@expressive-code/plugin-line-numbers` — see `references/expressive-code.md`.
- Don't add `starlight-package-managers` (pre-Astro 7, last shipped January 2026). Hand-write `<Tabs syncKey="pkg">` instead.
- `starlight-openapi` (HiDeoo) — generates documentation pages from OpenAPI/Swagger specs. The standard answer for API reference on a Starlight site.
- `starlight-links-validator` (HiDeoo) — validates internal links at build. 0.25.3 supports Starlight 0.41 / Astro 7 and is Sätteri-aware; earlier versions were not, and Starlight's own repo skipped link checking for a while because of it.
- For machine readability (`starlight-llms-txt`, `starlight-page-actions`, MCP), see `references/llm-friendly.md` — including how to check whether a community plugin is still alive.
- Pagefind search is built in and needs no setup; it indexes at build time, so search results won't reflect `astro dev` content.

## Multi-repo docs

The current mechanism for pulling Markdown from other repositories is a **custom content loader** (Content Layer API, Astro 5+), not a build-time clone or pull script and not git submodules. Starlight's maintainers confirm a loader that fetches files from GitHub and returns them is the supported approach. Astro's `glob()` loader won't do it directly, since it derives slugs from a common base — mapping `packages/x/docs/thing.md` to a sensible URL, or `README.md` to something other than `/readme`, is the work.

**The catch worth knowing before designing this:** Starlight's Markdown processing — aside directives, clickable heading anchors, RTL code block support — applies only to content loaded through `docsLoader()`. Content from a custom loader or another collection does not get it by default. Extend it with `markdown.processedDirs`:

```js
starlight({
  markdown: {
    processedDirs: ['./src/data/reviews/'],   // paths relative to project root
  },
}),
```

Set this for every directory holding Markdown that isn't loaded by `docsLoader()` — including anything a custom multi-repo loader writes — or asides and heading anchors will silently not render there. (The sibling option is `markdown.headingLinks`, default `true`.) This holds regardless of processor — see `references/markdown-pipeline.md`.

Two operational consequences: pull-request previews need wiring so a Markdown change in a source repo builds a preview of the docs site rather than just the source repo; and content lives away from the config that renders it, so an author editing Markdown can't see whether a plugin their page depends on is installed. Both are architecture decisions rather than authoring ones, but they determine whether contributors can check their own work.
